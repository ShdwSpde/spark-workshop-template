Does it work? The data

We tested Spark against plain Claude on the same model, with hidden answer keys, and audited nine months of our own logs (March to November 2026). Here's what held up, including what didn't.

2.6× the work per active week

Before Spark (Jan to Mar 19, 2026): about 20,000 lines of code and text per active week across our repos. With Spark: about 53,000, and 73,000 since October. Models and our own speed improved too, so read this as consistent with Spark helping, not proof.

8 of 8 vs. 6.5 of 8

A game card with 8 planted errors, reviewed three times each. Spark's reviewer caught 7, 7.5 and 8. Plain Claude caught 6.5 every time. Neither raised a false alarm.

About 18 errors stopped before going public

Fabricated quotes and newspaper clippings in AI-drafted games, misattributed quotes, a wrong auction date, minstrel-coded imagery, an unsupported photo label. About 10 more got out, and every serious one had skipped review or changed after it.

6 of 19 rules held

We checked whether corrections stuck. Rules enforced by code or tests held. Rules written only as notes came back, some within days. Two failed silently on our own live site until we built a check for them.

What plain Claude already does, and what Spark adds

Knows well-known history and catches famous misquotes+Knows your archive: cites the exact source line, tells sourced fact from your own pitch copy
Reads an image against its caption, when asked+Checks every time it's wired in, and marks a draft blocked until a person has read the findings
General style and accessibility advice+Your house rules, enforced by a written rubric and scripted checks
Forgets everything between sessions+Memory, state files and a decision journal, so work resumes where it stopped
Waits for a prompt+Scheduled briefings, drift checks and an eval suite that run on their own

What didn't work, and what we changed

A review only helps if it runs

Our worst public errors went out without any review at all. A wrong caption on a stock certificate was caught by a person, not the system. Plain Claude spots the same error when asked. Now: the reviewer is a separate agent with a fresh context. Next: the weekly briefing lists every public page that hasn't been reviewed.

Notes don't enforce, checks do

Of the 15 corrections we could check, 9 slipped at least once. The ones that held were code: a unit test, a hard cap. Now: mechanical rules are scripts with their own tests, and every new mistake becomes a test case.

Nothing has been signed off as fully validated

Our reviewer has blocked and flagged dozens of drafts but has never marked a public item fully validated. That's by design (a person signs off, not the AI), and it also means the reviewer works best as a brake on drafts. We're turning it into a release gate.

Method: git history across 15 repos; controlled reviews with hidden answer keys, 10 runs, same model; hand audits of our validation and activity logs. Counts from the logs are approximate. The workshop teaches you to run the same tests on your own setup.

How It Works

One entry point. Eight specialized agents. Shared state that IS the institution.

YOU │ ▼ ┌─────────┐ │ SPARK │ ← routes to the right agent │ (CAO) │ └────┬─────┘ ┌──────┼──────┐ ▼ ▼ ▼ Agent 1 Agent 2 Agent 3 ... Agent 8 │ │ │ ▼ ▼ ▼ ┌────────────────────────────┐ │ STATE FILES (markdown) │ │ portfolio · priorities │ │ decisions · people │ │ validation · memory │ └────────────────────────────┘

Every agent reads the same files. Every agent writes to them. If the system loses its AI tomorrow, the state files tell the next person everything. Markdown in a git repo: no database, no vendor lock-in, human-readable, diffable.
